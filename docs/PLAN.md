# go-gostcrypto — план реализации

Библиотека на Go, реализующая российские криптографические стандарты:
ГОСТ Р 34.12-2015 (блочные шифры), ГОСТ Р 34.13-2015 (режимы работы),
ГОСТ Р 34.11-2012 (хэширование), ГОСТ Р 34.10-2012 (электронная подпись).

---

## 1. Источники (изучены)

| Стандарт | Первоисточник | Англоязычный эквивалент |
|---|---|---|
| ГОСТ Р 34.12-2015 «Блочные шифры» | tc26.ru `GOST_R_3412-2015.pdf` | RFC 7801 (Кузнечик), RFC 8891 (Магма) |
| ГОСТ Р 34.13-2015 «Режимы работы блочных шифров» | tc26.ru `GOST_R_3413-2015.pdf` | **RFC отсутствует** — только первоисточник |
| ГОСТ Р 34.11-2012 «Функция хэширования» | ТК 26 | RFC 6986 (Стрибог) |
| ГОСТ Р 34.10-2012 «ЭЦП» | ТК 26 | RFC 7091 |
| Параметры кривых, VKO, KDF, HMAC | Р 50.1.113-2016 | RFC 7836, RFC 4357 |
| PKIX / ASN.1 / OID | — | RFC 9215 (заменил RFC 4491) |
| MGM (AEAD) | Р 1323565.1.026-2019 | RFC 9058 |
| ACPKM (перевыработка ключа) | Р 1323565.1.017-2018 | RFC 8645 |

Замечания по статусу:

* **ГОСТ 34.12-2018 / 34.13-2018** — межгосударственные версии тех же
  стандартов, алгоритмически идентичны версиям 2015 г. Отдельной реализации
  не требуют.
* ГОСТ Р 34.13-2015 — единственный из четырёх, у которого нет RFC-перевода.
  Все формулы и контрольные примеры для режимов взяты напрямую из
  официального PDF ТК 26 (раздел 5 и приложение А).

## 2. Ключевые технические решения и «ловушки»

Это самая ценная часть плана: ниже собраны места, в которых реализации
ГОСТ чаще всего расходятся между собой.

### 2.1 Кузнечик (ГОСТ Р 34.12-2015, разд. 4)

* Блок 128 бит, ключ 256 бит, 10 раундов (9 x LSX + финальный X).
* Поле GF(2^8) по модулю `p(x) = x^8 + x^7 + x^6 + x + 1` → `0x1C3`.
* Коэффициенты `l(a15..a0)`:
  `148, 32, 133, 16, 194, 192, 1, 251, 1, 192, 194, 16, 133, 32, 148, 1`.

  > **Опечатка в RFC 7801 §4.2.** В тексте RFC второе слагаемое записано как
  > `32*delta(a_15)` вместо `32*delta(a_14)` — errata ID 6928 (статус
  > *Reported*). Проверено по первоисточнику: в ГОСТ Р 34.12-2015 формула (1)
  > содержит `32 * delta(a14)`. **Ориентироваться на русский текст.**

* `R(a15..a0) = l(a15,..,a0) || a15 || .. || a1`, `L = R^16`.
* Развёртывание ключа: `Ci = L(Vec128(i))`, i = 1..32; 8 раундов Фейстеля
  `F[k](a1,a0) = (LSX[k](a1) xor a0, a1)` на каждую пару ключей, 4 итерации →
  K1..K10. `K1 = k255..k128`, `K2 = k127..k0`.
* **Порядок байт:** `a15` — старший байт, то есть `block[0]`. Частая ошибка —
  зеркальная загрузка блока.
* **Оптимизация:** объединённые таблицы LS — 16 таблиц по 256 записей по
  16 байт = 64 КиБ на зашифрование плюс столько же на расшифрование.
  Обратное преобразование требует отдельных таблиц для `S^-1 L^-1`.
* **Побочные каналы:** табличная реализация уязвима к кэш-таймингу. Решение —
  вынести табличный путь под build tag и держать медленный «портируемый»
  путь по умолчанию, либо явно задокументировать модель угроз (см. §6).

### 2.2 Магма (ГОСТ Р 34.12-2015, разд. 5)

* Блок 64 бита, ключ 256 бит, 32 раунда.
* S-блоки — набор `id-tc26-gost-28147-param-Z` (RFC 7836, приложение C).
  `t(a) = Pi7(a7) || .. || Pi0(a0)`, где **`Pi0` применяется к младшему
  полубайту**. Проверено на контрольном примере `t(fdb97531) = 2a196f34`.
* `g[k](a) = t(a + k mod 2^32) <<< 11`.
* Ключи: `K1 = k255..k224` ... `K8 = k31..k0`; повтор 3 раза, затем раунды
  25–32 в обратном порядке `K8..K1`.
* Раунд 32 использует `G*`, который **не меняет половины местами**.
* **Главное отличие от ГОСТ 28147-89:** ключ и данные разбираются как
  big-endian, а не little-endian. Реализация 28147-89 «в лоб» даст другие
  подключи и другой шифртекст.

### 2.3 Стрибог (ГОСТ Р 34.11-2012)

* `g_N(h, m) = E(LPS(h xor N), m) xor h xor m`, `E` — 13 раундов,
  `K[1] = K`, `K[i] = LPS(K[i-1] xor C[i-1])`, i = 2..13.
* IV: 512 бит → `0^512`; 256 бит → 64 байта `0x01`.
* Дополнение: добавить `0x01`, затем нули до 64 байт (в порядке потока).
* Финал: `h := g_0(h, N)`, затем `h := g_0(h, Sigma)`; для 256 бит — `MSB_256`.
* **Порядок байт — главная ловушка.** В стандарте и в RFC 6986 все векторы
  записаны в обратном порядке байт относительно потока данных. Пример:
  `M1` в RFC — это ASCII-строка `012345...012`, записанная задом наперёд, а
  контрольное значение `486f64c1...` — байтовый разворот «естественного»
  дайджеста `...c1646f48`. Практическое решение: хранить состояние как
  `[8]uint64` в little-endian и загружать байты потока напрямую;
  выдавать дайджест в том же порядке индексов.
* **Оптимизация:** `LPS(x) = xor по i=0..7 от T[i][byte_i(x)]` — 8 таблиц по
  256 записей типа `uint64` = 16 КиБ. Одна таблица покрывает и прямой ход,
  и развёртывание ключей.
* 12 констант `C1..C12` (по 64 байта) из §6.5 — переносить побайтно, с
  автоматической сверкой по контрольным примерам.

### 2.4 Режимы работы (ГОСТ Р 34.13-2015)

Формулы взяты из раздела 5 первоисточника.

| Режим | Параметры | Формула |
|---|---|---|
| Простая замена (ECB) | — | `Ci = eK(Pi)`, длина кратна `n` |
| Гаммирование (CTR) | `0 < s <= n` | `CTR1 = IV \|\| 0^(n/2)`, `CTRi+1 = CTRi + 1`, `Ci = Pi xor Ts(eK(CTRi))` |
| Гамм. с ОС по выходу (OFB) | `s <= n`, `m = n*z` | `Yi = eK(MSBn(Ri))`, `Ri+1 = LSB(m-n)(Ri) \|\| Yi`, `Ci = Pi xor Ts(Yi)` |
| Простая замена с зацеплением (CBC) | `m = n*z` | `Ci = eK(Pi xor MSBn(Ri))`, `Ri+1 = LSB(m-n)(Ri) \|\| Ci` |
| Гамм. с ОС по шифртексту (CFB) | `s <= n`, `n <= m` | `Ci = Pi xor Ts(eK(MSBn(Ri)))`, `Ri+1 = LSB(m-s)(Ri) \|\| Ci` |
| Выработка имитовставки (MAC) | `0 < s <= n` | OMAC1 / CMAC |

Особенности, из-за которых **нельзя переиспользовать `crypto/cipher`**:

* **CTR:** синхропосылка `IV` имеет длину `n/2`, а не `n`; счётчик занимает
  младшую половину блока. Плюс поддерживается усечение гаммы до `s < n`,
  чего в `cipher.NewCTR` нет.
* **CBC / OFB:** регистр сдвига `R` имеет длину `m = n*z`, то есть
  синхропосылка может быть длиной в несколько блоков. При `z = 1` совпадает
  с классикой.
* **CFB:** сдвиг регистра на `s` бит, а не на `n`.
* Для `s = n` и `z = 1` наши реализации обязаны совпадать с классическими —
  это отдельный тест.

Дополнение сообщения (§4.1) — три процедуры:

1. **Процедура 1** — дополнение нулями. Неоднозначна, требует знания
   исходной длины.
2. **Процедура 2** — `P || 1 || 0..0`, всегда однозначна, всегда удлиняет.
3. **Процедура 3** — процедура 2, но только если последний блок неполный.
   **Обязательна для режима имитовставки**, не рекомендуется для остальных.

Выработка вспомогательных ключей MAC (§5.6.1):
`R = eK(0^n)`; `K1 = R<<1` (xor `Bn`, если старший бит `R` равен 1);
`K2 = K1<<1` (xor `Bn`, если старший бит `K1` равен 1),
где `B64 = 0x1B`, `B128 = 0x87`.

### 2.5 Электронная подпись (ГОСТ Р 34.10-2012)

* Кривая в форме Вейерштрасса `y^2 = x^3 + ax + b (mod p)`, **`a != -3`**
  (в контрольном примере `a = 7`). Значит:
  **`crypto/elliptic` неприменим** — `elliptic.CurveParams` реализует
  только `y^2 = x^3 - 3x + b`, а его generic-реализация к тому же
  задепрекейчена. Нужна собственная арифметика.
* Подпись: `e = alpha mod q` (если `e = 0`, то `e = 1`); случайное `0 < k < q`;
  `C = kP`; `r = x_C mod q`; `s = (rd + ke) mod q`; подпись = `r || s`.
* Проверка: `v = e^-1 mod q`; `z1 = sv`; `z2 = -rv`; `C = z1*P + z2*Q`;
  принять при `x_C mod q == r`.
* **Кодирование подписи:** `r` и `s` — big-endian, дополненные нулями до
  ровно 32 (или 64) байт. В контрольном примере RFC 7091
  `s = 0x01456C64...` — со старшим нулевым полубайтом. Обрезание ведущих
  нулей ломает совместимость.
* **Порядок байт при переводе хэша в `alpha`** — вторая по частоте ошибка
  совместимости после Стрибога. Разрешать не «по здравому смыслу», а
  эмпирически: сверять с реальным сертификатом из RFC 9215, приложение D
  (есть примеры и для 256-, и для 512-битного ключа).
* Кривые в форме скрученного Эдвардса (`id-tc26-gost-3410-2012-256-paramSetA`
  и `512-paramSetC`, RFC 7836 §5.2) допускают полные формулы сложения —
  предпочтительны с точки зрения устойчивости к побочным каналам.
* Наборы параметров к реализации:
  * 256: `id-GostR3410-2001-CryptoPro-{A,B,C}-ParamSet` (RFC 4357),
    они же `id-tc26-gost-3410-2012-256-paramSet{B,C,D}` (RFC 9215, прил. C);
    `id-tc26-gost-3410-2012-256-paramSetA` (Эдвардс, RFC 7836);
    тестовый набор из RFC 7091 §7.1.
  * 512: `id-tc26-gost-3410-12-512-paramSet{A,B}` (RFC 7836, прил. A.1),
    `paramSetC` (Эдвардс, прил. A.2); тестовая кривая — RFC 9215, прил. E.

### Соответствие интерфейсам стандартной библиотеки

* Шифры → `cipher.Block`.
* CBC при `z = 1` → `cipher.BlockMode`; CTR при `s = n` → `cipher.Stream`.
  Остальные конфигурации — собственные типы с явными параметрами `s`, `m`.
* Стрибог → `hash.Hash` плюс `encoding.BinaryMarshaler`/`BinaryUnmarshaler`
  (соглашение Go для возобновляемого состояния хэша).
* `gost3410.PrivateKey` → `crypto.Signer`.
* MGM → `cipher.AEAD`.
* Собственные значения `crypto.Hash` регистрировать через
  `crypto.RegisterHash` в диапазоне выше стандартных.

## 5. Тестирование

1. **KAT** — все контрольные примеры из приложений стандартов и RFC.
   Уже извлечены (см. §7), покрывают каждый режим для обоих шифров.
2. **Промежуточные значения.** Стандарты приводят не только вход и выход, но и
   значения после каждого раунда и на входе базового алгоритма. Тестировать
   их отдельно — это резко ускоряет отладку.
3. **Round-trip** — `Decrypt(Encrypt(x)) == x` для всех режимов и всех
   допустимых `s`, `m`; то же для процедур дополнения 2 и 3.
4. **Fuzzing** (`go test -fuzz`) — round-trip, дополнение, разбор ASN.1,
   `UnmarshalBinary` состояния хэша.
5. **Кросс-проверка** с независимой реализацией (`gogost`, OpenSSL
   gost-engine) на случайных данных — в отдельном пакете с build tag, чтобы
   не тянуть зависимость в основной модуль.
6. **Совместимость с `crypto/cipher`** — при `s = n`, `z = 1` результаты CBC
   и CTR обязаны совпасть со стандартными реализациями Go.
7. **Бенчмарки и `testing.AllocsPerRun`** — контроль отсутствия аллокаций в
   горячем пути.

## 6. Безопасность

* `math/big` **не является constant-time**. На этапе 4 допустим ради
  корректности, но до релиза скалярное умножение должно перейти на
  собственную арифметику поля с фиксированным окном и полными формулами
  сложения (Renes–Costello–Batina) либо на форму Эдвардса.
* `k` в подписи — только из `crypto/rand`. Дополнительно предусмотреть
  детерминированный режим в духе RFC 6979 как опцию.
* Табличные реализации шифров и хэша уязвимы к кэш-таймингу.
  Задокументировать модель угроз явно; по возможности дать безтабличный путь.
* Обнулять чувствительные буферы (раундовые ключи, `K1`/`K2`, состояние хэша)
  там, где это осмысленно, понимая ограничения GC в Go.
* Библиотека должна оставаться набором примитивов; протокольные решения
  (выбор `s`, `m`, уникальность синхропосылок) — ответственность вызывающей
  стороны, но это надо описать в README. Требования к синхропосылкам заданы
  в §4.2 ГОСТ Р 34.13-2015: для CBC и CFB — непредсказуемая,
  для CTR — уникальная, для OFB — уникальная либо непредсказуемая.

### 7.7 Подпись, 512 бит

RFC 7091 содержит **только** 256-битный пример. Тестовая кривая для
512 бит — RFC 9215, приложение E; сквозные примеры (сертификат, запрос,
CRL, подписанные 512-битным ключом) — RFC 9215, приложение D.3.
Полный набор `d, k, e, r, s` брать из ГОСТ Р 34.10-2012, приложение А.2.
