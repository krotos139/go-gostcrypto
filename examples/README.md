# Примеры

Готовые к запуску программы. Каждая — самостоятельный `main`, запускается
прямо из каталога библиотеки:

```bash
go run ./examples/<имя> [аргументы]
```

| Программа | Что показывает |
|---|---|
| [`hash-file`](hash-file) | Хэширование файла «Стрибогом» 256 и 512 бит |
| [`encrypt-file`](encrypt-file) | Шифрование файла «Кузнечиком» в режиме MGM, ключ из пароля |
| [`sign-cms`](sign-cms) | Выработка ключа, выпуск сертификата, открепленная подпись CMS и её проверка |
| [`inspect-signature`](inspect-signature) | Разбор чужой подписи `.p7s` или `.sig`: кто, чем, когда, метка времени, цепочка |
| [`envelope-cms`](envelope-cms) | Шифрование документа получателю по его сертификату |
| [`keycontainer`](keycontainer) | Чтение транспортного ключевого контейнера `.pfx` |
| [`legacy`](legacy) | Устаревшие ГОСТ 28147-89 и ГОСТ Р 34.11-94 |

## Пароли

Программы, которым нужен пароль, берут его из переменной окружения
`GOST_PASSWORD` — так он не попадает в историю команд и в список
процессов:

```bash
GOST_PASSWORD='мой пароль' go run ./examples/keycontainer контейнер.pfx
```

В настоящем приложении пароль спрашивают у пользователя, не показывая
ввод.

## Чего примеры не делают

`sign-cms` и `envelope-cms` сами выпускают себе сертификаты, чтобы
работать без внешних зависимостей. В жизни сертификат выпускает
удостоверяющий центр по запросу — его умеет строить
`gostasn1.CreateCertificateRequest`, — а ключ обычно хранится в токене и
наружу не выходит.

Проверка подписи в примерах означает только её математическую верность.
Построение цепочки доверия, проверка срока действия и отзыва — отдельная
задача, которую библиотека намеренно не решает.
